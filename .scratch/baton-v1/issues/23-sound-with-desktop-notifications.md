# 23: Sound with desktop notifications

**What to build:** `baton watch` can play a sound itself when it shows a desktop notification, with `pw-play` or `paplay`. It is off unless I set it in the config.

First tried: the `sound-name` hint of `notify-send` (the desktop plays the sound). On a real Cinnamon 6.0.4 the daemon advertises the `sound` capability, but the desktop's own setting `org.cinnamon.desktop.sound event-sounds = false` makes `canberra-gtk-play` answer "Sound disabled", and no sound was heard with the hint. A desktop that has event sounds off is common, so Baton plays the file itself and does not send the hint (a desktop that honored both would play twice).

**Blocked by:** 12

**Status:** done (real check of the player by hand only)

- [x] `~/.config/baton/config.toml` gets an optional table `[watch]` with `sound = "<value>"`. A missing table, a missing key or an empty string means no sound: nothing is played and the `notify-send` arguments are exactly what they were before this ticket (no hint).
- [x] `sound` is either a **name** from the freedesktop sound theme, for example `"message-new-instant"`, or an **absolute path** of a file (`/…`, or `~/…`, `~` being `$HOME`). A name is looked up as `<dir>/freedesktop/stereo/<name>.<ext>` with `ext` one of `oga`, `ogg`, `wav` (in this order), in `$HOME/.local/share/sounds`, then `/usr/local/share/sounds`, then `/usr/share/sounds`; the first file that exists wins. The user directory is searched first so that tests can put a fake theme there.
- [x] Validated when the config is read by `baton watch`, which stops before it starts on a wrong value, with an error that names the key and the file and does not quote the value, and the other commands are not affected: a name is letters, digits, `.`, `_` and `-` only (at most 64 characters); a path must be absolute or start with `~/`, with no NUL or newline. The file is looked up when `baton watch` starts: a name that is found nowhere, or a path that is not a regular file, is a config error too (the error says where it looked). Not a string is an error.
- [x] With a sound set, each desktop notification (not a Telegram message while away) is followed by the player started for the resolved file: `pw-play <file>` if `pw-play` is on `PATH`, else `paplay <file>`. The player runs in the background and never delays the notification or the next look of the watcher; a player that fails or hangs more than 10 s is killed and noted as one warning line on stderr (at most one such line per distinct message, so a missing player does not flood). If neither player is on `PATH`, `baton watch` prints one warning at start and goes on without a sound. Sounds of notifications that arrive while an earlier one is still playing may overlap; there is no queue.
- [x] A notification that falls back to the desktop after a failed Telegram request also plays the sound (the desktop is the channel then).
- [x] The setting `event-sounds` of the desktop is not consulted: setting `sound` is the way to ask for a sound. `DESIGN.md` says so and records the Cinnamon finding above as measured on Oct 23, 2026 (`GetCapabilities` has `sound`; `event-sounds false`; `canberra-gtk-play -i message-new-instant` printed `Failed to play sound: Sound disabled`).
- [x] Tested at the binary seam only (AGENTS.md), with stubs for `notify-send`, `pw-play` and `paplay` (add `pw-play` and `paplay` stubs to `internal/batontest` like the others, recording their calls) and a fake theme under the Env's `$HOME/.local/share/sounds/freedesktop/stereo/`: no `[watch]` table / empty sound → no player call, old `notify-send` arguments; a name → `pw-play <that file>` after a `waiting_approval` notification; no `pw-play` on `PATH` → `paplay`; neither → one warning at start, notification still sent; extension order; a path and a `~/` path; a name found nowhere and a relative path stop `baton watch` with a config error and call nothing; a hanging player does not hold up the next notification; no player call for a Telegram message while away; the fallback to the desktop plays.
- [x] `DESIGN.md` (the `baton watch` / notifications section and the config format with the new table) and the README's `config.toml` documentation describe `[watch] sound`, replacing what the earlier hint-based draft wrote there. The README status row for `baton watch` says: players checked only against stubs unless the lead has tried it for real.
